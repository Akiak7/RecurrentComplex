**Diagnostic build 3 — implementation and coverage notes**

Build 3 includes the demonstrated child-layout reuse correction documented in [the returned-run analysis](dregora-diagnostic-run-2026-09-27.md). Each scripted chunk pass receives its previously prepared or serialized child layout instead of accidentally preparing a new one. The diagnostic activation, retention and observation mechanisms are unchanged from build 2. This is a test candidate, not a confirmed Dregora fix or a published release.

The tester needs only the [three-step guide](dregora-diagnostic-tester-guide.md). There is no A/B matrix or request to gather separate files. The earlier investigation remains historical evidence, not a new testing assignment.

Activation: `config/reccomplex-diagnostics.properties` must explicitly contain `enabled=true`. With the file absent, false, unreadable or invalid, diagnostics stay OFF. No JVM properties are read. The supplied opt-in file selects all dimensions and locations. Optional dimension, area and exact structure-ID filters remain available to developers through the diagnostic properties file; the tester does not need them. No RC, RLTweaker, OTG or other non-diagnostic configuration is written.

One server/world session creates one unique `diagnostics/recurrentcomplex/RC-diagnostic-<timestamp>-<suffix>.zip`. Single-player uses its integrated server. An atomic snapshot is written in the background at the start and every 30 seconds; normal server shutdown writes the final snapshot synchronously. Opening another world or restarting creates another filename, even when timestamps collide. Previous sessions are never automatically deleted. The login message identifies the file; inspecting that message is not a testing requirement. Disk errors can leave the last successful snapshot stale, and abrupt termination can lose observations since that snapshot. Subsequent successful snapshots retain an output-error marker.

The ZIP includes:

- `session.txt`: build ID/source revision/dirty flag, jar hashes for relevant mods, all loaded mod IDs/versions, effective simple RC and RLTweaker RC fields, RC generation config categories, diagnostic limits, world seed/dimension/type/options, coverage counters, and last anonymous player positions. Startup data is kept separately from recent events.
- `structures/context-*.txt`: each tracked structure's initial summary and initial detail, plus a bounded tail of completion/entry/terrain events. Initial BEGIN, placement, planned bounds, result and entry creation have reserved summary slots so verbose samples cannot displace them. UUIDs connect initial generation, later completion and saved-entry cleanup/load operations. Completion first observed after eviction or outside capture is explicitly marked `INITIAL_CONTEXT_UNAVAILABLE`; it never claims to recover the missing initial pass.
- `recent-events.txt` and `evictions.txt`: bounded recent session events and notices identifying contexts that were lost. Total loss counters remain even after individual eviction notices themselves expire.

Retention favors saved structure entries: up to 128 saved structures and 32 other/in-flight attempts, each with up to 64 Ki characters of initial detail and 32 Ki of later detail, plus reserved summary slots. Failed placements and ordinary unsaved decoration cannot consume the saved-structure allowance. Entire contexts are evicted by least recent activity within their allowance. Metadata is capped at 1 Mi character, general recent events at 256 Ki, and eviction notices at 128 Ki. All caps and lost-record counts are included in the file. Payload bounds are characters, not a promised ZIP size or heap limit. In-memory strings and snapshot construction can use tens of MiB at saturation; no live-pack performance measurement has been made.

The existing observation hooks still capture actual generation callers (including reflective RLTweaker callers), IDs, chosen Y, full/clipped bounds, seeds, stages, failures/skips, saved entry changes, existing placement samples and fixed support observations. Caller stacks have an explicit 14-frame limit. There are at most 64 active support watches, five positions per watch, Y±4 direct block windows and 16 relevant population-end observations per watch. Watches report eviction, expiry and unload. Whole-context eviction also prevents subsequent terrain observations for that context. Immediate before/after observations stay with initial evidence; later own/neighbor population observations go in that structure's later history. Bounds fallback points and candidate ray hits are labeled. A bounded observation is not a complete ground survey or proof that a later writer was OTG.

Anonymous player position and view direction are sampled every 100 player ticks, on login/logout and at shutdown where available. At most 32 players are tracked. Names, player UUIDs, accounts, IPs, save names, mod source paths, general command/account expressions and unrelated files are not collected. Structure UUIDs and world seeds are intentional diagnostic identifiers. Exception types and filtered callers are recorded instead of arbitrary exception messages; path-like strings are redacted as a fallback. OTG preset/structure files and complete DH/pregenerator configurations are not copied into the report; evaluated placement evidence and mod identity are captured instead. Missing metadata is marked unavailable.

Empty population/check activity is counted rather than logged with a stack per chunk. File compression uses the fastest ZIP level on one background writer. Generation callbacks collect bounded records and perform only the previously bounded, already-loaded-chunk reads. No extra worldgen random calls, chunk-providing reads, placement evaluations, generation changes, event rescheduling or worldgen lock changes were introduced. Logging and observation still cost CPU/memory; sustained pregeneration may evict a faulty structure before a player reaches it. A run without captured failure is inconclusive.

The separate optional SelectivePlacer coordinate fix remains in commit `7379fd31`. Build 3 adds only the child-layout correction described above; defaults, cleanup, generation mode, event timing and locks remain unchanged. It makes no claim to fix the separate floating-height report.
