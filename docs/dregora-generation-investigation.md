**Confirmed handler selection.** RLTweaker only constructs `RecurrentHandler` when RC is loaded and its RC master switch is enabled. Inside that constructor, Manage gates replacement of one listener; cleanup registration is outside that gate. The four booleans require a Minecraft/server restart.

| RC master | Manage | Partial | Population-start handler | Cleanup |
| --- | --- | --- | --- | --- |
| OFF | either | either | Native `RCForgeEventHandler.onPreChunkDecoration` | Not registered by this integration |
| ON | OFF | either | Same native handler | Runs if Clean ON |
| ON | ON | ON | Same native handler | Runs if Clean ON |
| ON | ON | OFF | RLTweaker `RCHandler.onPreChunkDecoration`, if replacement succeeds | Runs if Clean ON |

Native handler: `PopulateChunkEvent.Pre` → `WorldGenStructures.decorate(..., null)` → lookup pending entries, `checkChunk`, `complementStructuresInChunk`, static and natural planning → Volts `StructureGenerator`. Volts' `PARTIALLY_SPAWN_NATURAL_STRUCTURES` constant is true.

RLTweaker's replacement reflects into Volts' `WorldStructureGenerationData.get/structureEntriesIn/checkChunk`, `WorldGenStructures.complementStructuresInChunk/planStaticStructuresInChunk`, selectors, `randomSurfacePos`, and the same `StructureGenerator` fluent API. Its natural planning calls `.partially(false, chunkPos)`. Static planning still calls native Volts and remains partial. The separate terrain-decoration handler and decoration generation path are not replaced by this switch. The replacement wraps its work in `synchronized(wsgData)`; native Volts has its own narrower metadata synchronization and chunk locks. No locking change is proposed.

There is **no separate RLTweaker partial-generation engine**. With partial ON, RLTweaker leaves the native handler in place. Setup/reflection failures must be checked in startup logs; config intent alone is not proof of successful replacement. See [master gate](https://github.com/Meldexun/RLTweaker/blob/522cc7139dc78bf06f2a399b002a98afdd2c6def/src/main/java/com/charles445/rltweaker/RLTweaker.java#L156), [handler and cleaner](https://github.com/Meldexun/RLTweaker/blob/522cc7139dc78bf06f2a399b002a98afdd2c6def/src/main/java/com/charles445/rltweaker/handler/RecurrentHandler.java), and [config](https://github.com/Meldexun/RLTweaker/blob/522cc7139dc78bf06f2a399b002a98afdd2c6def/src/main/java/com/charles445/rltweaker/config/ConfigRecurrent.java).

Therefore the disabled-versus-enabled/partial-ON observations are unresolved, not evidence of different partial engines. With cleanup OFF in both, these controls select the same native path. With cleanup ON, only the enabled run installs the cleaner, changing saved records, overlap checks and spawn limitations. Prior cleanup can also leave irreversible missing records in a reused test world after the cleaner is disabled. Exact startup settings, listener/call-path evidence, restart history, jar hashes, and identical starting save state distinguish these possibilities. A fresh disabled run with intact records cannot be explained by this integration's cleaner.

**Cutoffs: confirmed mechanics and separate hypotheses.** Partial generation clips writes to decoration tiles `[16*cx+8, 16*cx+23]` in X and Z. `RCStructureBoundingBoxes.rasterize(..., true)` subtracts 8 before dividing by 16, consistent with those bounds, including negative coordinates. Record the actual seam coordinates: a seam at remainder 8 differs from a physical chunk edge at remainder 0.

After an initial successful pass, `StructureGenerator` stores UUID, structure and generation IDs, fixed full bounds, transform, seed and instance NBT. It immediately complements intersecting tiles already marked checked, skipping the initial tile. Later population-start events find that entry and generate their clipped section using its saved placement; they do not recalculate height. Normal save/reload retains this information. `firstTime=false` means the initial pass happened, not that all tiles finished; `preventComplementation=false` allows further passes. Checked flags are global tile history, not per-structure proof of successful completion.

Completion is skipped for `preventComplementation=true`, a missing registry structure, or missing instance data after the initial pass. Instance serialization failures log an error but can leave an unusable entry. Completion's generation result is not acted on here; failed writes need explicit diagnostics. The initial Post event precedes saving/adding the current entry. Ordinary Lite Pre/Post events do not cover completion passes. RC sight-delete commands also remove records, though there is no evidence they were used. See [generator](https://github.com/Akiak7/RecurrentComplex/blob/b2c72188d5f3de75b991ab16fe5bd7a8aa65acd1/src/main/java/ivorius/reccomplex/world/gen/feature/StructureGenerator.java#L128), [completion](https://github.com/Akiak7/RecurrentComplex/blob/b2c72188d5f3de75b991ab16fe5bd7a8aa65acd1/src/main/java/ivorius/reccomplex/world/gen/feature/WorldGenStructures.java#L205), and [saved data](https://github.com/Akiak7/RecurrentComplex/blob/b2c72188d5f3de75b991ab16fe5bd7a8aa65acd1/src/main/java/ivorius/reccomplex/world/gen/feature/WorldStructureGenerationData.java).

Two distinct RLTweaker cleanup operations are confirmed:

| Trigger | What is removed | Consequence |
| --- | --- | --- |
| Threshold of initial structure Post events per dimension (default 100; not an entry-count check) | Every current entry via `removeEntry`, including incomplete partial and custom entries; checked sets remain | Pending structures disappear from chunk/instance indexes, preventing future lookup; overlap/limitation history also changes |
| Server world load | Serializes data, removes `entries`, `checkedChunks`, `checkedChunksFinal`, then reloads it; preserves `customEntries` | Pending records and checked history disappear in memory, including after reopening a frontier save |

This is a demonstrated compatibility hazard for unfinished partial generation, not proof it caused the reported screenshots. The periodic Post hook can remove older pending structures; normally the currently posting structure is added afterwards. World-load wiping is effective in memory even without assuming it immediately rewrites the disk file. RLTweaker's separate Minecraft structure-file cleaner targets `MapGenStructureData` (default Village/Mineshaft), not this RC record store.

A conservative future RLTweaker fix would preserve entries eligible for further completion and their required checked history in both cleanup paths. Merely checking `firstTime`, or disabling only periodic cleanup, is insufficient. Native partial entries do not acquire a reliable per-tile-success ledger here, so a more selective cleanup needs its own design/evidence. No cleanup or RLTweaker setting has been changed.

Other cutoff hypotheses remain: a required population event never ran; records were absent/invalid before the pass; a completion pass failed; or blocks were generated then overwritten by later population. Non-partial natural writes reach beyond the normal decoration tile and may meet terrain that is not finally populated. That makes the ON improvement plausible, but does not prove overwriting or resolve the disabled-run discrepancy.

**Floating heights.** `SelectivePlacer` chooses source blocks at its baseline. Rays transform these into world positions; `RayAverageMatcher` samples matching ground offsets, ignores rays with no hit, optionally rejects a spread, and applies a robust average. `GenericPlacer` combines factors and selects a permitted Y; the generator fixes that placement for later completion. Neither average matching nor spread rejection guarantees support under every block. The exact tower's generation type, preset, baseline, source/destination expressions, transformers and sampled positions are still needed.

`rayAverageMaxHeightSpread=0` disables only the `maxSpread > 0` rejection. It neither restores a different averaging algorithm nor changes population timing. The continued floating observation therefore rules out that setting as a sufficient remedy; it does not establish another cause. `avoidPlacerChunkGeneration=false` permits placement reads outside already generated terrain. When true, generated-chunk checks still do not establish that later population is finished. IvToolkit's world cache lazily obtains block states from the world; it is not a snapshot of final terrain.

OTG 9.7's `OTGChunkGenerator.populate` calls `ObjectSpawner.populate`. Its population-start callback posts Forge Pre synchronously, reaching RC. Both BO3 and BO4 paths then process resources. The BO4 path also spawns BO4s and smoothing after Pre and before Post; smoothing can replace terrain above a cut with configured material, including air. Thus supporting terrain **can** change after RC chooses Y. Whether the failing tower's preset and columns actually undergo those writes is unproven. Do not blame the late `ForgeWorld.replaceBlocks` call: that method immediately returns in this revision. See [ObjectSpawner](https://github.com/PG85/OpenTerrainGenerator/blob/c96b563dbf267e3a9e132aafa98cfffc8071a771/common/src/main/java/com/pg85/otg/generator/ObjectSpawner.java#L156), [Forge event bridge](https://github.com/PG85/OpenTerrainGenerator/blob/c96b563dbf267e3a9e132aafa98cfffc8071a771/platforms/forge/src/main/java/com/pg85/otg/forge/events/ForgeEventHandler.java#L103), [smoothing](https://github.com/PG85/OpenTerrainGenerator/blob/c96b563dbf267e3a9e132aafa98cfffc8071a771/common/src/main/java/com/pg85/otg/customobjects/structures/bo4/smoothing/SmoothingAreaColumn.java#L126), and [disabled replacement sweep](https://github.com/PG85/OpenTerrainGenerator/blob/c96b563dbf267e3a9e132aafa98cfffc8071a771/platforms/forge/src/main/java/com/pg85/otg/forge/world/ForgeWorld.java#L1233).

**Demonstrated Volts defect and local patch.** The optional `SelectivePlacer` availability filter queried chunks using structure-local X/Z, ignoring placement origin, rotation and mirror. A 32-block footprint at X=160, Z=-160 should test chunks near (10,-10), not (0,0)/(1,0). The minimal patch transforms coordinates for the availability query only; downstream surface positions remain local and the empty-filter fallback is preserved. Defaults are unchanged. This defect is inactive with the supplied `avoidPlacerChunkGeneration=false`, so it is not an explanation for that configuration's floating tower.

`SelectivePlacerTest` failed on the original code and passes with the patch; it covers all eight rotation/mirror combinations at a translated, negative-Z location, disabled behavior, fallback, and no added block/chunk-fetch or random calls. `WorldStructureGenerationDataCompletionTest` covers save/reload, both modeled cleanup mutations, and exact tile coverage across negative coordinates. All seven focused tests pass with Java 8 using `./gradlew --offline test --tests '*SelectivePlacerTest' --tests '*WorldStructureGenerationDataCompletionTest'`. Cleanup tests characterize Volts' response to RLTweaker's mutations; they do not run RLTweaker or OTG. No game reproduction, full-pack validation, or release was performed.

**Proposed opt-in diagnostics (not implemented).** Use a default-OFF trace restricted to dimension, a small chunk rectangle and optionally structure ID, with a bounded record count and an explicit truncation marker. Instrument the common generator and direct pre-complement call, not just Lite events or the native event handler; otherwise the RLTweaker replacement or completion passes would be missed.

- At startup, record loaded jar filenames/hashes, effective RC/RLTweaker values, and native/replacement/cleanup registration or failure. At generation, identify actual caller path (native natural/static, RLTweaker natural, decoration, script/other), population chunk, nesting depth and thread. A bounded stack capture when enabled can identify the reflective path without modifying RLTweaker.
- Record structure ID, generation-info ID, existing seed, rotation/mirror, chosen lower Y, full bounds, clip bounds, initial/completion/pre-completion stage, success/failure and skip reason. Use a monotonic diagnostic correlation ID, then associate the actual saved UUID after `addEntry`; do not create random IDs or force lazy generator accessors just for logging.
- At existing ray evaluation points, record the already selected samples/hits/misses, excluded terrain, min/max offsets and returned Y. Do not rerun the placer, predicate or random sampling. Record entry add/remove/load and the relevant checked flags, instance-data presence and complement prevention; retain a bounded removal caller/reason so cleanup can be distinguished from load or commands.
- Observe a fixed, bounded set of the same support columns before RC writes, after its pass, at population Post and after neighboring population. Use only `ChunkProviderServer.getLoadedChunk` and direct reads from returned chunks; if absent, record **unavailable**, never air or height zero. Capture block states at fixed support positions, a bounded direct column scan, and existing population flags. Never call a chunk-providing getter, world height/biome lookup, or OTG unloaded-terrain helper for diagnostics. Keep unloaded/evicted samples explicitly unknown.
- Distinguish RC's own block changes from later ones using the immediate-after-RC observation. A changed column by Post implicates later population but does not identify its writer. If needed, add a coordinate-filtered observation at OTG's existing smoothing/resource writes, recording existing old/new values and caller without issuing extra writes. Clear watch data on unload and report lost coverage. Diagnostic code must never consume the worldgen random stream, cancel events, trigger terrain generation, change settings, or select a different placement.
